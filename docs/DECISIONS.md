## 2026-08-03: スコアの真実は `chip_states`、`game_events` は記録

### 決定

- **`chip_states.holder_player_id` がスコアの唯一の真実**。`src/lib/scoring.ts` は `chip_states` のみから
  スコアを計算し、`game_events` は一切参照しない。
- **`game_events` は人が読むための記録**であり、スコアの計算には使わない。
- サイドゲーム（オリンピック／ドラコン／ニアピン）の精算も同様で、真実は
  `olympic_logs` / `dracon_logs` / `niapin_logs`。`game_events` に入るサイドゲーム行はテキストの記録にすぎない。

### 理由

チップの現在の持ち主を毎回イベントの畳み込みで再計算すると、イベントが1行でも欠けた／壊れた瞬間に
全プレイヤーのスコアが狂う。持ち主を直接持つほうが、リアルタイム同期（`onSnapshot`）とも相性がよい。

### この不変条件から出る帰結（重要）

ログ行を書き換えても**スコアは自動では変わらない**。したがってログ編集機能では、
書き換えた行が「そのチップの最新の移動」であるときにだけ `chip_states` も同時に更新する。

- **最新行の修正** → `chip_states.holder_player_id` を新しい移動先に更新（＝スコアが直る）
- **最新行の削除** → `chip_states.holder_player_id` を `from_player_id` に戻す（＝その移動を取り消す）
- **過去行の修正・削除** → 記録の表示だけ直す。UI で「スコアは変わりません」と明示する

過去行を直したときに `chip_states` を触ってはいけない。その後の移動履歴を無視して持ち主を
上書きしてしまい、ログとスコアが食い違うため。

## 2026-08-03: `game_events` の不変性を捨て、ホストによる修正を許可した

### 決定

`firestore.rules` の `game_events` を `allow update: if false`（不変）から `allow update: if true` に変更した。
ログ行の修正・削除はプレイ画面から**ホストのみ**行える（クライアント側 UI での制御）。

### 理由

1. **不変性は実効的な防御になっていなかった**。このアプリは Firebase Auth を導入しておらず、
   `games` / `players` / `chip_states` を含む他のコレクションはすべて `if true` で開いている。
   `game_events` だけ更新禁止にしても、スコアの真実である `chip_states` は誰でも書き換えられるので、
   「ログは改ざんできない」という保証は元々成立していない。守れていない一線を守っているふりをするより、
   実運用の要求に応えるほうが正直である。
2. **実運用でミスの訂正需要が上回った**。ラウンド中の入力ミス（渡し先違い、ホール番号のズレ、
   サイドゲームの誤入力）は普通に起きる。誤操作を「戻す」操作で訂正すると、ログに
   「誤操作」と「訂正」の2行が残って読みにくくなり、後から誰も経緯を追えなくなる。

### 補償

- 修正した行には `edited_at` を記録し、UI に ✎ マークを出す（黙って書き換わらない）
- 編集導線はプレイ画面のみ。結果画面のログは閲覧専用
- 終了したゲームを直すにはホストが明示的に「ゲームを再開して修正する」を押す必要がある

### 将来 Auth を入れるときの方針

Firebase Auth（匿名認証で可）を入れる場合、`game_events` の `update` / `delete` は
`request.auth.uid == games/{roomCode}.host_player_id` 相当の条件に絞る。
そのときは他コレクションの `if true` も併せて見直すこと（`game_events` だけ絞っても意味がない）。

## 2026-08-03: 終了したゲームはホストが再オープンできる

### 決定

結果画面にホストのみ「🔓 ゲームを再開して修正する」を置き、`games/{roomCode}.status` を
`finished` → `playing` に戻す。結果画面は `onSnapshot` でゲームドキュメントを購読しており、
`playing` になった全員の端末が自動でプレイ画面へ遷移する。

### 理由

修正の導線をプレイ画面に一本化するため。結果画面にも編集 UI を作ると、同じ編集ロジックが
2画面に重複し、「終了後に静かに書き換わる」動きにもなってしまう。
再オープンという明示的な1アクションを挟むことで、参加者全員に修正中であることが伝わる。

### 副作用（意図通り）

- `HomeClient` の「開催中のゲーム」は `status !== 'finished'` で絞っているため、
  再オープンしたゲームはトップ画面に再び現れる
- ゲーム履歴は `saveToHistory` が既存ドキュメントを上書きしないため影響を受けない

## 2026-08-03: サイドゲームのログ行は「置き換え」で保存する

### 決定

オリンピック／ドラコン／ニアピンの入力を保存するとき、`addDoc` する前に
同じホール・同じ種目の既存 `game_events` 行を削除する。
ログのサイドゲーム行をタップすると、そのホールの入力モーダルが既存値付きで開く。

### 理由

以前は同じホールを再入力するたびに `addDoc` でログ行が増え続け、同じホールの結果が
複数行並んで矛盾して見えるバグがあった（精算そのものは `*_logs` 側で正しく上書きされていたため、
ログの表示だけが食い違っていた）。サイドゲーム行に専用の編集モーダルを作らず既存の入力モーダルを
再利用したのは、順位入力の UI をもう一つ作って二重管理にしたくなかったため。

既存データとの互換のため、サイドゲーム行の判別は新フィールド `game_events.side_game` を優先し、
無ければ `description` 先頭の絵文字（🏅/🏌️/📍）にフォールバックする（`src/lib/eventLabel.ts`）。

## 2026-08-03: Firestore のオフライン永続キャッシュを有効化した（複数タブ方式）

### 決定

`src/lib/firebase/client.ts` を `getFirestore` から
`initializeFirestore(app, { localCache: persistentLocalCache({ tabManager: persistentMultipleTabManager() }) }, 'chip-golf')`
に変更し、IndexedDB による永続キャッシュを有効にした。
併せて `src/components/OfflineIndicator.tsx` を `layout.tsx` に置き、オフライン中は画面上部にバーを出す。

### 理由

ゴルフ場は電波が悪い。永続キャッシュが無いとキャッシュはメモリのみで、リロードした瞬間に
画面が真っ白になる。永続キャッシュがあれば圏外でリロードしても直前のゲーム内容が出る。

**`persistentSingleTabManager` を採用しない理由**: 単一タブ方式は IndexedDB のリースを1タブしか
持てず、2枚目のタブで Firestore クライアントの起動そのものが失敗しうる。ゴルフ場で共有リンクを
踏み直して2枚目が開くのは実際に起きる操作なので、リーダー選出で共有される複数タブ方式を選んだ。

`initializeFirestore` は同じ App に対して2回呼ぶと throw するため、`getApps().length === 0` で
App の二重初期化を避けているのと同じ理由（dev の HMR）で `try/catch` して `getFirestore` に
フォールバックする `initDb()` を挟んでいる。

### オフライン表示バーは #scroll-root に padding-top を入れる

各画面のヘッダーはスクロールコンテナ `#scroll-root` 内の `sticky top-0 z-10`。バーを
`fixed top-0` で出すだけだとヘッダーを覆い、「ゲーム終了」やメニューが押せなくなる。
`OfflineIndicator` はバーの実測高さを `#scroll-root` の `padding-top` に流し込み、
ヘッダーをバーの下へ押し出す（sticky はスクロールコンテナのパディングボックス基準で止まるため、
スクロール中もヘッダーがバーの直下に貼り付く）。オンラインに戻ったら `padding-top` を戻す。

バーを下端に置かなかったのは、ネイティブでは AdMob バナーが `BOTTOM_CENTER` を占有するため。

### 検証で分かった既存の落とし穴（今回は直していない）

**Firestore の書き込み Promise（`addDoc` / `updateDoc` / `setDoc`）はサーバーに到達して初めて
解決する。** オフライン中はローカルキャッシュとリスナーには即座に反映されるが `await` は解決しない。
実測で確認した影響は2種類ある。

1. **`await` の後続処理がオフライン中は実行されない**
   `PlayClient.doTransfer()` は `await updateDoc(chip_states)` → `addDoc(game_events)` の順。
   オフラインでチップを移動すると持ち主とスコアは即座に反映されるが、**ログ行は追加されない**
   （接続が戻って `updateDoc` が解決した時点で初めて追加される）。
   接続が戻る前にタブを閉じると `chip_states` の書き込みは IndexedDB のミューテーションキューに
   残って次回起動時に流れるが、**`addDoc` は呼ばれないままなのでログ行だけ永久に失われる**。
   スコアの真実は `chip_states` なのでスコアは狂わないが、記録は欠ける。

2. **スピナーが止まらない**
   「`setSaving(true)` → `await` 書き込み → `setSaving(false)`」の形は回りっぱなしになる。該当箇所:
   `LobbyClient.tsx:98` / `ResultClient.tsx:121` / `PlayClient.tsx:1333,1342` /
   `ChipsManageClient.tsx:237` / `ChipsTemplateClient.tsx:98` / `OlympicModal.tsx:51` /
   `SingleWinnerModal.tsx:45`

どちらも永続キャッシュの有無に関わらない既存の挙動だが、キャッシュを入れて初めてオフライン運用が
現実的になるため踏む頻度は上がる。UI の作り替えは別タスクとする。

## 2026-09-27: チップのタッチドラッグは長押し開始にし、端末ごとに OFF にできるようにした

### 決定

- `TouchSensor` の開始条件を「8px 動いたら即」から **250ms の長押し（tolerance 5px）** に変更。
  チップの `touch-action` は `none` → `manipulation`。
- タップ判定はドラッグ有効時「250ms 未満」、無効時「400ms 未満」。長押しして離しても移動先モーダルは開かない。
- ☰メニューに「チップのドラッグ操作」ON/OFF。**端末ごとの好み**なので `localStorage['chipDragEnabled']` に保存し、
  Firestore には持たない（デフォルト ON）。OFF でもタップ→移動先選択で全操作ができる。

### 理由

片手でスクロールしようとしてチップの上から指を動かすと、`touch-action: none` のため 100% ドラッグになり
誤移動が起きていた（ユーザーの声）。長押し開始にすると素早いスワイプはネイティブスクロールになる。

## 2026-09-27: ホール送り忘れを「同じホールで同じチップが2回動いた」ことで検知する

### 決定

- 現ホールで既に移動したチップを再び動かそうとしたら、記録する**前に**確認モーダルを出す
  （［H{次}に進めて記録］［H{現}のまま記録］［キャンセル］）。
- ただし直前の移動から 60 秒以内は出さない（置き直し＝誤操作の修正とみなす）。最終ホールでも出さない。
- 「進めて記録」は `games.current_hole` を更新してから、そのホール番号で `game_events` に記録する。
- スクロールしても現在ホールが見えるよう、sticky ヘッダー下に HOLE 表示を常設（タップでホール操作カードへスクロール）。

### 理由

ベガスゴルフでは 1 ホールで同じチップが 2 回動くことはほぼ無いので、設定なしで送り忘れを高精度に検知できる。
記録前に聞くため、ログの事後修正（`edited_at`・`chip_states` 同期ルール）とは無関係に済む。
時間経過での通知はプレーペースの個人差で誤報が多いため採用しなかった。
ヘッダー行にホールのピルを入れる案は 375px 幅で既存ボタンが収まらないため、下段の帯にした。

## 2026-09-28: 送り忘れの後始末（ホール番号の一括修正）とホール変更の全員通知

### 決定

- ログ修正モーダルでチップ移動行のホール番号を変えたとき、「この後のチップ移動の記録もまとめて同じだけずらす」
  「現在のホールも同じだけずらす」を選べる（既定はどちらもON）。対象行・後続行・`current_hole` は `writeBatch` で一括更新し、
  各行に `edited_at` を記録する。
- 一括でずらすのは**チップ移動行のみ**。サイドゲーム行は対象外（精算の真実は `*_logs` にあり、各入力モーダルで直す）。
- 後続行の一括変更では `chip_states` を触らない（ホール番号はスコアに無関係。修正した行自体が最新なら従来どおり同期）。
- ずらした結果が 1〜総ホール数を外れる行があれば一括修正は不可（理由を表示）。
- 誰かがホールを進めた／戻したら、全員の端末で HOLE 帯を光らせ、「HOLE n に進みました／戻しました」を表示し、
  振動させる（Android のみ）。初回ロードでは出さない。アニメーションは key 変更で再生する。
- （同日追記）表示は自動で消さず、✕で閉じるまで出したままにする（邪魔にならないため・ユーザー判断）。次のホール変更で再表示。

### 理由

送り忘れは工夫しても防ぎきれないため、忘れても後から1回の操作で直せるようにした。
典型例（H3のままH4を記録→気づいて「次へ」）は、H4最初の行を直すだけで後続行と現在ホールまで揃う。
ホール変更の通知は、誰かが送ったことを全員が知ることで二重送りや送り忘れの思い込みを防ぐ。
